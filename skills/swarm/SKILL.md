Use the task after this skill mention as the team goal. If the user supplied a task, start the team directly.

With no task, or with `board` or a request to show the board, use `open_swarm_panel`. Use the specified `teamId`. If the user gives a title, find its ID with `list_teams` and ask which group they mean if several match. With no specified team, use the team already opened in this chat, or pass the current project's absolute `cwd` to find its latest team. If the project has no teams, open the returned empty panel and say that it is ready for a task. For an explicit request to inspect, message, pause, or resume an existing team, use the corresponding Hive Swarm tool instead of creating a second team.

## Do not do the technical work

As coordinator, delegate technical work — code edits, research, investigations, builds, tests, and review fixes — to workers. Your job is to size and split the work, read and judge reports, unblock dependencies, and communicate verified results to the user. Quick read-only lookups to answer the user are fine; never sit inside long inline edits while the swarm waits, and never edit worker-owned files while a worker is `working` or has queued `inboxCount > 0` (check `board_status` first, and cancel or wait before touching those files).

## Start the team

1. **Size lean and design disjoint file ownership**: Count the pieces that can genuinely proceed independently; use one worker for a tightly coupled change. Assign disjoint file ownership before anyone starts — two writers editing the same file is a failure mode to design out, not manage. Name workers for their job (`parser`, `verifier`, `docs`), never `agent-1`. Aim for one read-only verifier per 2–4 writers, with `waitFor` listing the responsible workers and an explicit check to run (a verifier reports and the author fixes). Default to read-only; set `writable: true` only for user-authorized edits. Keep at most 12 active workers; use `n` for identical shards or `tasks` for distinct slices under one `group`.
2. **Write self-contained public briefs, or fork warm context**: Every brief is posted publicly on the board and is everything a fresh worker receives — state what it owns, what it must not touch, and what "done" looks like. Set a crisp `taskLabel` (`<= 96` chars) on each member so the Overview task list is immediately scannable. Pass `fork: "coordinator"` on a member in `start_team` (or `add_member`) when a worker needs the files already read, decisions made, and reasoning in this coordinator conversation instead of starting cold; pass `fork: "<teammate>"` in `add_member` to inherit a teammate's saved chat.
3. **Give concurrent writers isolated worktrees**: For writers that edit or build at the same time, set `worktree: true` (each starts from the committed Git revision) while leaving readers and verifiers on the shared checkout. Have each author commit in its worktree and leave integration into the main checkout to the coordinator/user.
4. **Verify models and routes first (Strict Model Lock)**: Use the current local project's absolute `cwd`. Resolve explicitly requested or role-matched models and reasoning efforts via `list_models` before launching — keep Strict Model Lock by default and never silently substitute an unconfigured model or provider. Keep the user's requested model or current chat's model (omit `model` for the runtime default unless requested or role-matched). Pass `fallbackModel` / `fallbackEffort` on the team or member only when the user opts into automatic quota failover.
5. **Follow Overview Plan discipline and call `start_team` once**: Preserve the user's file scope, deliverables, and turn limit. Include a concise `goalLine` (`<= 140` chars), per-member `taskLabel` (`<= 96` chars), and 1–6 outcome `threads` (`[{id, title, goal, members}]`) so Overview tracks outcomes (`Blocked` -> `Active` -> `Queued` -> `Done`). Call `set_team_plan` (`{ goalLine, tasks, threads }`) only when scope, labels, or roster actually change — never churn plans mid-round. In a Goal, set `coordinator: false` so the current chat is the sole coordinator; in a regular one-turn chat, set `coordinator: true` only when you want `@coordinator` to summarize completed worker rounds in the background. Under Codex Desktop, worker threads stay attached to the parent conversation instead of cluttering the sidebar.
6. **Open the Swarm UI**: Immediately call the Codex app tool `open_in_codex` with the exact `openInCodex` arguments returned by `start_team` or `open_swarm_panel` (omit `threadId` unless the user asks for another chat). If the host has no panel tool or it reports an error, fall back to `open_board` as the inline MCP App. In either case, give the user a clickable Markdown link labeled `🐝 Open Swarm UI` to the returned `url`, along with the work split and actual team status.

## Coordinate on the board

- **`@name` is a wakeup doorbell, never a CC**: Write teammate names without `@` when merely referencing them in prose. Use `@name` (or `@group`, `@#channel`) only for members who must take a turn next. Pass `wake: false` on `post_message` for thank-you, acceptance, or FYI notes so you never trigger a spurious extra turn. Address the parent chat as `@coordinator` (never invent `@lead` unless a worker is named `lead`). Brief builders and verifiers for direct peer-to-peer handoffs (`@builder` <-> `@verifier`), reserving `@coordinator` for final delivery, blockers, or scope changes. Reserve `@all` for genuine team-wide rules or interface decisions, never for status. A post with no recipient does not wake an idle member.
- **Cite `#seq` and finish with `[done]`**: Keep board posts concise (decisions, file paths/evidence, `#seq`, `@next`). Refer to earlier board posts by sequence number (`#4`, `#12`) instead of copy-pasting or summarizing one worker's report into another worker's message (`@verifier check #4 and #6`). Ask workers to start finished reports with `[done]`, avoid re-calling `read_board`/`list_models` when new messages are already delivered in the wake prompt, and never double-post their final report via `post_to_board` right before returning their turn-end report.
- **Visual timeline (`Screenshot: <path> | <caption>`)**: For UI/visual tasks, instruct UI authors or verifiers to include `Screenshot: <path> | <caption>` lines (workspace-relative or inside the workspace/data directory, `.png`/`.jpg`/`.jpeg`/`.webp`, `<= 10 MiB`, caption `1–140` chars) in their board post or report so Overview displays a safe visual timeline. Skip screenshots for pure backend, API, or documentation tasks.
- **Channels — keep `main` quiet**: For multi-area or larger swarms, split workstreams with `manage_channel` (`create`, `subscribe`, `unsubscribe`, `archive`). Everyone sees `main` plus their subscribed channels, so keep area chatter inside its channel (`channel`, `@#channel`) and reserve `main` for cross-area asks, decisions, and final results. Archive channels when an area finishes.
- **Wait without polling**: In a Goal, call `wait_for_board` with the last seen `since` cursor rather than polling `board_status` or `board_history` in a loop. If `hasMore` is true, continue from the last returned post. Act on stopped or stalled phases before issuing the next wait: read `[stall]` and structured `attention` issues (unaddressed `#seq`, unanswered mention, dependency root blocker) from saved facts without starting a diagnostic model turn. Use `board_history` with a cursor to read earlier posts.

## Roster, quota, recovery, and cleanup

- **Roster updates**: Look up the team first. Use `add_member` (including `taskLabel`) to invite a worker, `replaces` to transfer an idle worker's unfinished dependencies, and `fork: "coordinator"` or `fork: "<teammate>"` to inherit warm history. Update `set_team_plan` only if the scope or roster changes. Read-only workers can invite only read-only helpers. Use `retire_member` (member or shard group) once nothing depends on it; retirement is permanent — never retire as a pause, because idle waiting workers cost nothing. Use `set_team_title` for a requested rename.
- **Switch model on quota without killing history**: Never retire and re-add a worker that hits quota (`status: "quota"`). Use `set_member_model` (`effort: null` for the model default, `resume: true` to wake an idle member) so the worker keeps its saved conversation history (a history-preserving fork handles provider changes automatically). Verify configured and executed routes (`Verified route:` / active model) via `list_models` and member Journals.
- **Pause, cancel, recovery, and worktree cleanup**: `pause_team` pauses new dispatch without cancelling a running worker; use `cancel_turn` (pass `clearInbox: true` to drop stale queued posts) if a running worker must stop immediately. If a member has an unconfirmed run (`recoveryRequired`), inspect its Journal first and resolve explicitly with `resolve_recovery` (`action: "retry"` or `"dismiss"`). Use `remove_worktree` when the user asks to clean a checkout after its member retires or the team finishes (`force: true` only on explicit user request to discard uncommitted changes). The user can add eight turns from the board when the team reaches its turn limit.
