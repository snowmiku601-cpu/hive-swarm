---
name: hive-swarm
description: Coordinate a user-requested native DeepSeek Harness worker team and open its Swarm views.
---

Use this skill when the user asks for a Hive Swarm or to inspect an existing native team. Read operations and opening the panel never start a model.

## Do not do the technical work

Use the current chat as coordinator and delegate technical work — code edits, research, investigations, builds, tests, and review fixes — to native workers. Your job is to size and split work, judge returned reports, resolve blockers, and summarize verified results for the user. Quick read-only lookups to answer the user are fine; never sit inside long inline edits while workers wait, and never edit worker-owned files while a worker is `working` or has queued `inboxCount > 0` (check `hive_swarm_board_status` first, and cancel or wait before touching those files).

## Start the team

1. **Verify workspace and model route first (Strict Model Lock)**: Call `hive_swarm_list_models` before choosing a model or reasoning effort (`currentSession` reports the host-verified workspace and active model route for this chat when available). Keep Strict Model Lock by default and never silently substitute an unconfigured model or provider. Preserve the user's scope, limits, permissions, and preferred model in the team and member briefs. Pass `fallbackModel` / `fallbackEffort` on the team or member only when the user opts into automatic quota failover.
2. **Size lean, design disjoint file ownership, and pick work-group `threads`**: Count independent work pieces; use one worker for a tightly coupled change. Assign strict disjoint file ownership before anyone starts — two writers editing the same file is a failure mode to design out, not manage. Name workers for their job (`parser`, `verifier`, `docs`), never `agent-1`. Aim for one read-only verifier per 2–4 writers with `waitFor` listing the responsible workers and explicit checks to run (a verifier reports; the author fixes). Workers default to read-only (`writable: false`); request `writable: true` only for user-authorized edits. Keep at most 12 active workers (and stay within DSH's 8-subagent pool cap per root chat when you want zero sidebar clutter — exceeding 8 active subagents falls back to ordinary native sessions). Set `threads` (`[{id, title, goal?, members?}]` — `goal` is optional) and/or per-member `thread` (`id` or `title`) to group workers into specialized honeycomb work-group cells in Swarm Overview and Hive Graph (worker-invited helpers automatically inherit the inviter's thread when `thread` is omitted).
3. **Follow strict-mode `n` / `tasks`, `brief <= 4000`, and Overview Plan discipline**: Under OpenAI Responses strict-mode schemas, pass `null` for unused optional fields: on each member, keep `n: null` and `tasks: null` for a single worker (never set both; put a single worker's checklist in `brief`), and use either `n` (2–8 homogeneous shards) or `tasks` (2–8 distinct slice strings, `<= 2000` chars each) only when sharding. Keep every member `brief <= 4000` characters, `goalLine <= 140` characters, and `taskLabel <= 96` characters. Call `hive_swarm_set_team_plan` (`{ goalLine, tasks: [{member, label}], threads }`) only when scope, labels, or roster actually change.
4. **Write self-contained public briefs, and understand `fork: "coordinator"` caveats**: Briefs are public on the board and are everything a fresh worker receives — state what it owns, what it must not touch, and what "done" looks like. Pass `fork: "coordinator"` only when a worker genuinely needs completed prior coordinator turns (or `fork: "<teammate>"` in `hive_swarm_add_member` to inherit a teammate's saved session). **Important `fork: "coordinator"` caveats on DSH**:
   - DSH forks copy **completed turns only** (`turn/end`), so an in-flight coordinator turn (including files read and tool calls made in the current turn before `hive_swarm_start_team`) is **excluded** from the child's forked history.
   - Avoid `fork: "coordinator"` when the parent chat has prior failed/HTTP `402`/error turns or noisy chatter — those earlier turns are copied verbatim into every forked child. Prefer a crisp, self-contained `brief` instead.
   - If `fork: "coordinator"` is called during Turn 1 before any completed `turn/end` (`session/fork-unavailable`), DSH gracefully starts a clean session with a note rather than crashing. Note that `fork` cannot be combined with `worktree: true`.
5. **Avoid `sharedWriterActive` serialization — isolate concurrent writers (`worktreeMode: 'local'` or `parallelWriters: true`)**:
   - **Serialization warning**: When `parallelWriters` is `false` (the default), setting `writable: true, worktree: false` on multiple workers hard-serializes them to **1 active writer at a time** (`sharedWriterActive`, surfaced as `blockedReason: "shared-writer-active"` in `hive_swarm_board_status`) regardless of `concurrency`! Never set `writable: true` on read-only researchers/reviewers, and never expect `writable: true, worktree: false, parallelWriters: false` workers to run concurrently.
   - **Two parallel-writer options**:
     - Use `worktree: true` with `worktreeMode: "local"` on `hive_swarm_start_team` when writers edit/build concurrently in Git — `"local"` places worktrees under `<repoRoot>/.hive-swarm-worktrees/<teamId>/<member>` on a named branch `hive-swarm/<shortTeamId>/<member>` (preserving repo-root relative paths, `node_modules`, and single-drive Windows paths, unlike `"external"` which uses `<profileDir>/.hive-swarm/worktrees/`). Subagents share parent `cwd`, so `worktree: true` workers run as isolated native sessions (`session/create` + `🐝 @member` title). Have each author commit in its worktree and leave integration to the coordinator/user.
     - Pass `parallelWriters: true` on `hive_swarm_start_team` (with `concurrency` up to `8`) when concurrent writers have strictly disjoint file ownership in the shared checkout and won't contend on shared build caches/lockfiles.
6. **Respect DSH sandbox inheritance & Windows `workspace-write` limits**:
   - When the parent chat runs in `danger-full-access`, DSH inherits `danger-full-access` onto `writable: true` workers (both subagents and `worktree` fallback sessions) while keeping `writable: false` workers strictly locked to `read-only` (read-only workers always block `sandbox_permissions` escalation).
   - When the parent chat runs in `workspace-write` (or `read-only`), writable workers stay capped at `workspace-write` (never escalating above parent). On Windows under `workspace-write`, DSH's `WRITE_RESTRICTED` Low-integrity NTFS ACL sandbox blocks piped grandchild spawns (`next build`, `tsc`, `spawnSync(..., {stdio: 'pipe'})` -> `spawn EPERM`) and unpropagated directories; authorize `danger-full-access` on the parent session when full build pipelines are needed, or assign those checks outside confined workers.
7. **Call `hive_swarm_start_team` once**: Pass the current chat's actual workspace, a clear goal, optional `goalLine`, bounded `turnLimit`, `coordinator: false` when the current chat coordinates, `threads`, `parallelWriters` / `worktreeMode`, and the member plan. Non-worktree workers run as hidden native DSH child subagents under this parent chat (falling back gracefully to ordinary sessions when unavailable); never launch an external MCP board or a second scheduler.

## Coordinate on the board

- **Inspect and open views**: Use `hive_swarm_board_status`, `hive_swarm_read_board`, and `hive_swarm_board_history` to inspect a known team. Pass `seqs: [4, 12]` (1–20 post numbers) to `hive_swarm_read_board` to fetch exact cited `#seq` posts directly without paging. Open the native Swarm view with `hive_swarm_open_swarm_panel` for its exact `teamId`, or open the bee-marked `Swarm` Start card and select the team explicitly. Never pick the latest team globally or claim another session's history; keep the native DSH theme and workspace context.
- **`@name` is a wakeup doorbell, never a CC**: Post handoffs with `hive_swarm_post_message`. Write plain names without `@` when merely referencing teammates in prose, and use `@name` (or `@group`, `@#channel`) only for members who must act next. Pass `wake: false` on `hive_swarm_post_message` for thank-you, acceptance, or FYI notes so you never trigger a spurious extra turn. Address the parent chat as `@coordinator` (never invent `@lead` unless a worker is named `lead`). Encourage direct peer-to-peer handoffs (`@builder` <-> `@verifier`) in briefs rather than routing intermediate steps through `@coordinator`; reserve `@coordinator` for final delivery, blockers, or scope changes, and `@all` for genuine team-wide rules.
- **Cite `#seq` and finish with `[done]`**: Keep board posts concise (decisions, file paths/evidence, `#seq`, `@next`). Refer to prior board posts by sequence number (`#4`, `#12`) instead of copy-pasting or summarizing one worker's report into another worker's message (`@verifier check #4 and #6` — workers can fetch them via `hive_swarm_read_board({seqs})`). Ask workers to start finished reports with `[done]`, and avoid re-calling `hive_swarm_read_board` / `hive_swarm_list_models` when new messages are already delivered in the wake prompt.
- **Visual timeline (`Screenshot: <path> | <caption>`)**: For UI/visual tasks, instruct UI authors or verifiers to include `Screenshot: <path> | <caption>` lines (workspace-relative or inside the workspace/data directory, `.png`/`.jpg`/`.jpeg`/`.webp`, `<= 10 MiB`, caption `1–140` chars) in their board post or report so Overview displays a safe visual timeline. Skip screenshots for pure backend, API, or documentation tasks.
- **Channels — keep `main` quiet**: Split multi-area swarms with `hive_swarm_manage_channel` (`create`, `subscribe`, `unsubscribe`, `archive`; non-coordinator workers see `list`, `subscribe`, `unsubscribe`). Everyone sees `main` plus subscribed channels, so keep area chatter in its channel (`channel`, `@#channel`) and reserve `main` for cross-area asks, decisions, and final results. Archive finished channels.
- **Wait without polling (`timeoutSec` up to `900s`)**: Use `hive_swarm_wait_for_board` with the last seen `since` cursor and `timeoutSec` up to `900` (e.g. `300–900` seconds on DSH — never poll in 45s loops and never poll with `wait_agent`!). Continue from the last returned post when `hasMore` is true. Internal status posts do not cause spurious wakeups, `inputRequired` permission pauses wake immediately (`wokeBy: "input"`), and `[stall]` / `attention` facts appear when action is needed without starting a diagnostic model turn.

## Roster, quota, recovery, and worker protocol

- **Roster & model changes**: Scope member, channel, and model changes to the existing goal. Use `hive_swarm_add_member` (with `taskLabel`, `thread`, `replaces`, or `fork`), `hive_swarm_set_team_title`, and `hive_swarm_retire_member` (permanent — never retire as a pause; idle waiting workers cost nothing). Pass `dropDependency: true` on `hive_swarm_retire_member` (coordinator/owner only) when intentionally retiring an obsolete dependency so downstream `waitFor` lists remove it cleanly instead of deadlocking. Call `hive_swarm_set_team_plan` only when scope or roster changes. When a worker hits quota (`status: "quota"`), switch its model via `hive_swarm_set_member_model` (`effort: null` for model default, `resume: true` to wake) to keep its conversation history instead of retiring and re-adding. Verify active/executed routes via `hive_swarm_list_models` and `Verified route:` entries in `hive_swarm_read_journal` / Journal.
- **Pause, cancel, recovery, and worktrees**: `hive_swarm_pause_team` stops new dispatch without cancelling a running worker; use `hive_swarm_cancel_turn` (pass `clearInbox: true` to drop stale queued posts) if an active worker must stop immediately — cancelling settles the active run cleanly in `runs.sqlite`. A timeout or missing response is not proof that native work stopped: inspect the saved owned Journal (`hive_swarm_read_journal`) first, then resolve explicitly with `hive_swarm_resolve_recovery` (`action: "retry"` or `"dismiss"`). Clean checkouts after retirement or completion with `hive_swarm_remove_worktree` (`force: true` only on explicit user request).
- **Worker turn-end protocol**: As a worker, finish by calling `hive_swarm_set_turn_outcome` for the assigned Hive turn with `state`, a concise `message` (start finished reports with `[done]` and cite earlier posts with `#seq`), `notify`, and `waitFor`. Do not double-post the same final report via `hive_swarm_post_message` before calling `hive_swarm_set_turn_outcome`. The host publishes the report only after matching durable claim/end, host quiescence, and a successful persistence flush. Other workers cannot impersonate your identity or outcome.
- **Safety boundaries**: Use the native Overview, Board, Members, Graph, and owned Journal to explain progress. Preserve existing sessions, user data, and unrelated plugins. Do not publish packages, expose credentials, change global model defaults, or broaden permissions as part of coordination.
